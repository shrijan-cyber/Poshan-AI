# PoshanAI integration sprint: repository matrix

Reviewed 2026-11-05. Existing source and the focused food/recipe audit are the authority for PoshanAI behavior. No external dataset, code package, or service was installed or imported.

| Repository | Useful area | License/data posture | Priority | Decision |
|---|---|---|---|---|
| [OpenNosh](https://github.com/RujitRaval/opennosh) | Source-qualified food records, separate source stores, provenance, private custom foods, ingredient snapshots | MIT app; community packs CC0; OFF data has separate ODbL/DbCL treatment; source-specific records stay separated | P0 | Adopt design principles only. Existing Node/Mongo implementation can use source-qualified IDs and snapshots without copying its Python/Postgres/Next application. |
| [INDB](https://github.com/vikx01/Indian-Nutrient-Databank-INDB) | Indian ingredients, recipes, nutrients and retention factors | No dataset redistribution license found in reviewed repository; derived from multiple third-party sources | P0 | Do not import. Seek written permission and source-level provenance/licensing first. |
| [Indian Nutrition Data](https://github.com/prabhubng/indian-nutrition-data) | Fast coverage candidate and cross-check discovery | Repo declares CC0, but upstream IFCT/Gopalan rights and record-level provenance are not established by that declaration | P0 | Do not import into production. Use only as a lead for an independently verified source/permission review. |
| [USDA FoodData Central](https://fdc.nal.usda.gov/) | Complementary food coverage with stable IDs and source nutrient records | FDC data is public domain/CC0; application-specific transformation still requires traceability | P1 | Keep existing isolated staging pipeline. No promotion without identity, units, edible basis, state and provenance review. |
| [Open Food Facts](https://world.openfoodfacts.org/) | Packaged products and barcode lookup | ODbL database and DbCL contents; attribution/share-alike obligations; images are separately licensed | P2 | Keep branded product records isolated from generic food composition records; no image reuse without per-image checks. |
| [Diet App](https://github.com/whiteravens20/diet-app) | Deterministic recipe composition, grocery/pantry and AI boundary patterns | AGPL-3.0-only plus repository notices; separate Nest/Next/Postgres architecture | P1 | Read workflow ideas only. Do not copy/adapt source pending legal review; PoshanAI already has deterministic selection and IFCT math. |
| [Mealie](https://github.com/mealie-recipes/mealie) | Recipe CRUD, meal planning, groceries and cooking workflow | AGPL-3.0; separate application stack | P2 | Product workflow reference only; no source copying or embedding. |
| [Taste Skill](https://github.com/Leonxlnx/taste-skill) | Layout, typography, spacing, visual hierarchy and responsive review prompts | MIT; image search/assets have separate attribution and licensing requirements | P2 | Applied selectively to Food Library hierarchy. No scripts, assets, or photos copied. |
| [OmniRoute](https://github.com/cheaper-inference/OmniRoute) | Optional OpenAI-compatible provider gateway | Provider privacy, retention, keys and licensing vary by upstream route | P3 | Do not change default Gemini or send user health data. Existing optional-provider research is sufficient; no gateway change. |
| [DSH-GOD](https://github.com/crackerghost/DSH-GOD) | Alternative inference ecosystem | Additional provider/tooling and account/security surface | P3 | Reject for this sprint: no material advantage over existing provider boundary established. |
| [Awesome LLM Apps](https://github.com/Shubhamsaboo/awesome-llm-apps) / [Awesome-LLM](https://github.com/Hannibal046/Awesome-LLM) / [free LLM APIs](https://github.com/open-free-llm-api/awesome-freellm-apis) | Discovery lists and examples | Each linked project/provider has independent license, privacy, quotas and maintenance | P3 | Discovery only; not a production dependency or provider approval. |
| [Free Claude Code](https://github.com/Alishahryar1/free-claude-code) | Experimental model routing | Third-party provider/session/config risk | P3 | Defer; do not alter global Codex settings or submit PoshanAI source. |
| [Capsule](https://github.com/hakiyaka/capsule) | Local context retrieval and expansion | Local tooling/hooks/config surface needs isolated review | P2 | Conditional synthetic-only POC after approval; do not stack compressors. |
| [Compaction](https://www.compaction.dev/codex) | Context reduction | Hook/platform compatibility uncertainty in existing environment | P2 | Defer pending Windows-safe isolated benchmark. |
| [CodeSight](https://github.com/Houseofmvps/codesight) / [lowfat](https://github.com/zdk/lowfat) | Indexing or terminal/context compression | Overlaps Capsule; Windows support and quality need independent evidence | P2 | Defer to avoid overlapping tools and unmeasured savings. |

## Outcome

P0 is provenance and licensing, not adding more rows. Keep IFCT and external-source records source-qualified. Next safest work is a reviewed staging pipeline, then catalog UI for values actually available. License-dependent imports, AGPL-derived code, production provider routing and global Codex changes require separate approval.

Previously documented provider and context research is in `ai-ecosystem-comparison.md`, `omniroute-evaluation.md`, `free-llm-provider-evaluation.md`, `codex-final-optimization-plan.md`, and `codex-token-optimization-comparison.md`; this sprint did not repeat their benchmarks.
