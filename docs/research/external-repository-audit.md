# PoshanAI external repository integration audit

**Reviewed:** 2026-11-02
**Scope:** Read-only research and recommendations. No package, API, repository, or dataset was installed or integrated.

## Executive summary

PoshanAI already has the essential authoritative nutrition path: a shared IFCT-backed catalog, a household recipe catalog, deterministic meal selection and backend nutrition arithmetic. External APIs should fill bounded gaps, not replace this path. The clearest candidate is packaged-product barcode lookup through Open Food Facts, isolated from generic IFCT foods because its database has ODbL share-alike conditions and label-derived values. FoodData Central may be useful as an isolated comparison/staging source, but it is US-centric and does not establish Indian food identity. No public API reviewed is a verified replacement for IFCT 2017.

The current Express/React application already has local OCR, report parsing, an OmniRoute/Gemini-compatible AI boundary, Redis/BullMQ queues and project-local Codex skills. The LLM examples suggest evaluation and schema-validation patterns that can be adopted inside the existing JavaScript service. They do not justify a Python service, agent framework, or new model vendor.

ECC has a native Codex marketplace/plugin path and MIT license. It overlaps substantially with the project’s installed skills and `AGENTS.md`; a full plugin would add a large surface including hooks and MCP configuration. Defer it pending a targeted capability comparison and review of hook/plugin trust. Do not combine native plugin install with legacy Codex sync.

## PoshanAI fit and constraints

The checked-in architecture is a JavaScript MERN application: React/Vite frontend; Node/Express/Mongoose backend; Redis/BullMQ for queued tasks. OCR is already local (`pdfjs-dist`, `tesseract.js`); nutrition uses the shared IFCT loader and deterministic recipes. The LLM gateway is OmniRoute-compatible and should remain bounded to its existing task. The repository also has an isolated FDC/Open Food Facts staging workflow; preserve its source namespaces and review gates.

The local data audit records 542 application IFCT rows and 20 recipe templates; it identifies unresolved source mapping/reuse permission, universal missing B12/fiber values and name collisions. See [nutrition-data-source-evaluation.md](nutrition-data-source-evaluation.md). Never fill those gaps by external name matching or guessed values. PoshanAI’s product boundary is nutrition awareness, not diagnosis or treatment.

The linked API’s own availability, data quality, terms, and license control use. Its current Food & Drink list contains a mixture of recipe, branded-food, and nutrition-analysis APIs; a listing alone does not verify their current status. ### Nutrition source conclusion

1. Keep IFCT 2017 as the current Indian food-composition source and resolve its provenance/reuse questions; no reviewed external API provides a better verified Indian replacement.
2. Add Open Food Facts only for user-requested branded barcode lookup, separately namespaced and labeled as package data, after ODbL review.
3. Continue using FoodData Central only in the current isolated staging/comparison workflow; preserve source-specific units, basis and nulls.
4. Reject API-generated nutrient estimates as authoritative plan math. Do not send medical reports, raw OCR, or personal diet descriptions to these services.

## Repository 2 — awesome-llm-apps

The [repository](https://github.com/Shubhamsaboo/awesome-llm-apps) is an example catalog, not a supported component library. Its root license is Apache-2.0; individual samples, assets, dependencies, and model/provider terms still need independent review. The showcased ecosystem is predominantly Python and includes Streamlit examples. Do not add a Python service merely to reuse a demo.

### Patterns worth adapting

| Pattern | PoshanAI application | Priority / effort / cost | Guardrails |
|---|---|---|---|
| Typed, schema-validated RAG output (e.g. [typed agentic RAG example](https://github.com/Shubhamsaboo/awesome-llm-apps/tree/main/rag_tutorials/agentic_rag)) | Keep the existing OmniRoute `aiService.js` boundary; validate the narrow instruction/swap response with current Joi/schema tools before persistence. The backend remains the owner of IFCT selection and macro arithmetic. | **P1**; low; no added token cost, modest validation/test work. | Adapt the pattern only; verify sample path/dependencies under Apache-2.0 and their own licenses before copying any code. No free-form recipe or macro generation. |
| Retrieval grounding and abstention | If retrieval has no validated food/source match, return unavailable/abstain; carry IFCT codes and source references through response. | **P1**; low-medium; no additional model calls. | No external result should silently fill a missing IFCT nutrient; preserve `null`. |
| Offline model mocks and failure-path tests | Mock OmniRoute responses/timeouts; assert invalid model references are rejected and static recipe instructions survive AI failures. | **P1**; low; zero token cost for tests. | Keep tests deterministic and provider-independent. |
| RAG quality/evaluation harness | Golden cases for household whitelist, allergies/dislikes, source citation, null nutrients, and report extraction. Measure retrieval and grounding independently from prose quality. | **P1**; medium; local compute/test maintenance, no API usage. | Do not use synthetic medical facts as truth fixtures; fixtures need reviewed provenance. |
| PDF/report extraction pipeline examples | Compare only against current local `pdfjs-dist`/`tesseract.js` parser where concrete failure evidence exists. | **P2**; medium; avoid cloud/OCR API costs and report disclosure. | Existing OCR is local; no new Python service unless a measured accuracy gap justifies it. |
| Agents, tool calling, long-term memory | No current need: recipes/food selection are deterministic and the AI task is bounded. | **P2 (defer)**; high governance/privacy surface and potentially more model calls. | Do not give an agent arbitrary food catalog or health-profile write tools. No report-memory persistence. |

The example repository’s primary value is workflow inspiration, especially tests that run against fakes and retrieval failure diagnostics. Existing project code already uses JS/Express, local OCR, IFCT retrieval, Joi validation, and an LLM fallback boundary. Preserve that design instead of introducing LangChain/Pydantic AI/Python solely for demonstration parity.

## Repository 3 — ECC

The official [ECC repository](https://github.com/affaan-m/ECC) is MIT-licensed and publishes a native Codex plugin. The repo’s counts change often; its current manifests/readme advertise hundreds of skills and many agents, hooks, and MCP configuration. Treat counts as vendor claims, not a quality guarantee. Official Codex installation documented by ECC uses `codex plugin marketplace add affaan-m/ECC` then `codex plugin add ecc@ecc`; Codex owns plugin lifecycle and hook trust. ECC also documents a legacy copied-sync route and explicitly warns against stacking install methods.

| Capability | Local overlap and fit | Priority / effort / cost | Recommendation / risk |
|---|---|---|---|
| Skills | Project has 11 local skills; `skills-lock.json` names selected tools. `AGENTS.md` already establishes PoshanAI constraints. ECC likely duplicates design, TDD, docs and security guidance. | **P2**; low to compare, ongoing context/token cost if hundreds load. MIT; review each skill’s content. | Do not install full skill bundle. If a gap appears, compare one candidate skill against existing instructions and select minimally. |
| Code review/security/test workflows | The repo currently has gravitas and a project test suite; ECC has review, security and verification workflows that may complement them. | **P1** candidate; medium evaluation; no direct API cost. Tool installation may add maintenance/context. | Pilot a single workflow only after checking it doesn’t duplicate `gravitas`, project scripts, or existing skills. Review commands before use. |
| Native Codex plugin | Officially compatible via Codex marketplace lifecycle. Native plugin bundles skills and may include MCP/hooks. | **P2**; medium; software is MIT/free, but adds context/tool surface. | If approved later, inventory existing plugin and marketplace state, inspect manifest and trust prompts, use one native installation route, then verify/remove cleanly. No legacy sync at same time. |
| Hooks and permissions | Local `AGENTS.md` gives repo policy; Codex requires explicit trust decisions for plugin hooks. Hooks can execute scripts and change behavior at runtime. | **P2**; high risk/maintenance; no metered API fee but shell/runtime overhead. | Leave hooks disabled/untrusted unless an exact required hook, source, permissions and behavior have been reviewed and explicitly approved. Never loosen project permissions. |
| MCP/context management | `.mcp.json` is present in IDE context and must be treated as potentially sensitive; do not overwrite it. ECC may ship additional MCP configuration. | **P2**; medium-high; external service/API usage could incur cost and send project context externally. | Do not merge configuration. Audit endpoints, environment expansion, scopes and data handling first; keep current project servers. |

### ECC compatibility conclusion

Native Codex support is documented and preferable to legacy file-copy sync if eventually selected. Compatibility does not imply project-specific safety or a minimal install. Current local skills and instructions overlap with ECC, while the complete native plugin may expose a larger surface than the narrowly useful review/security workflows. Defer installation; do a manifest-level overlap review first. Do not inspect or print `.mcp.json` contents during this audit.

## Prioritized implementation plan

1. **P0 — No external nutrition API integration.** Keep IFCT/recipe backend calculations; resolve source licensing and record-level provenance as documented in the local nutrition audit. Effort medium-high; benefit is protecting trust; no new API/token cost.
2. **P1 — Add local AI regression/evaluation cases.** Cover schema validity, grounded food IDs, refusal when grounding is absent, AI timeout fallback and prompt privacy. Effort low-medium; no provider token cost in mocked tests.
3. **P1 — Consider isolated Open Food Facts barcode lookup.** First complete ODbL/commercial counsel review and data-separation design; then prototype read-only barcode fetch with attribution, stale/missing-label behavior and consent. Effort medium; free API but request/hosting overhead; keep separate from IFCT.
4. **P1 — Evaluate ECC workflow overlap, not installation.** Compare one security/review workflow with installed `gravitas` and project checks; document exact useful delta. Effort low; no API cost.
5. **P2 — Only if user demand justifies it:** evaluate external fitness or recipe discovery services. Review current terms, quotas, privacy and coverage immediately before selection; no candidate is approved as nutrition authority.

No integration or package installation has been performed. Approval is requested before implementation or installation.
